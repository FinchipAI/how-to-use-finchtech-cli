# Task Market

## Chain identity

The reviewed production Task manifest enables creation on Base (`8453`), Injective (`1776`) and Avalanche C-Chain (`43114`); TEST uses Base Sepolia (`84532`). Read the available Task deployment and admission from the server and preserve the exact returned chain through preparation, funding, awards, reclaim and recovery. An authentication chain or CLI upgrade does not select the business chain. Report an actual completed action only after its wallet and server confirmation evidence.

## Requester

Use `task_market:discover`, `task_market:requester:read`, and `task_market:requester:write` as needed.

In a mounted Finch MCP harness, use `task_market_task_mine`, `task_market_task_get_draft`, `task_market_task_create_draft`, `task_market_task_update_draft`, and `task_market_task_delete_draft` for the requester's saved tasks. Use `task_market_task_prepare_publish`, `task_market_task_review_board`, `task_market_task_prepare_review`, and, only when explicitly requested, `task_market_task_prepare_reclaim` for publication and review. Wallet preparations return `walletIntent` and a structured `localAction`. Require CLI 0.5.1 or newer and check that installed help supports `--intent`, then execute the returned action using the same Account, wallet, endpoint and environment. The CLI fetches the immutable preparation and submits its wallet result with its active Session; no local MCP business grant is needed. A successful CLI result is a wallet receipt; re-read business state through MCP. Do not make a second manual confirm call after success. CLI 0.4.1 predates this handoff; upgrading the Skill alone does not upgrade the executable. Older CLI builds retain their existing preparation-file workflow during rollout. Draft `rewardAmount` and `perSubmissionReward` values are decimal USDC amounts; returned custody preparations use atomic-unit string fields such as `amountAtomic` and carry the authoritative `signingAuthority`.

### Save, resume and edit

These saved-task operations run in Remote MCP and require no new local CLI command or client upgrade. They use the existing requester read/write scopes; a bearer without those scopes must obtain that authorization through its Harness. Public discovery excludes drafts. Call `task_market_task_mine` to recover this Account's saved task IDs, then `task_market_task_get_draft` to read the selected Task and its complete ordered Goals. The owner reader also works for a published Task; another Account cannot use it to read private draft contents.

Before an edit, read the latest owner detail. Build the complete draft input from its current fields and `extraConfig`, change only the user-requested content, and set `expectedUpdatedAt` to that detail's `updatedAt`. This is a complete replacement, so retain unchanged settings, each Goal's ID/configuration/scope, and both fixed `official_growth` Goals when present. Send only input fields, with `publishNow: false`; omit `imageLocator` or use null because Task covers are retired. The server validates ordinary versus advanced Goal permissions and the merchant Goal quota; the two official Goals do not consume that quota. A valid complete list can contain five merchant Goals plus two official Goals.

Copy `title`, `description`, `goal`, `rewardAmount`, `rewardCurrency`, `participationModel`, `structure`, `taskType`, `requireProof`, `requiresHuman`, `requiresTwitter`, `autoSettle`, `settlementMode`, `deadline` and `startAt` from the Task detail. Preserve `category` and `platform` when non-null, and `chainId` when non-null. Flatten these present `extraConfig` fields into the edit input: `allowMultiple`, `perSubmissionReward`, `targetCount`, `requiredKeywords`, `targetHandle`, `targetTweetUrl`, `minimumXFollowers`, `minimumXAccountAgeDays`, `minimumXTweets`, `requireXVerified` and `delayedAutoCoveragePct`. Use `maxSubmissions` for `targetCount` when present. For each Goal send only `id`, `goalType`, `scope`, `required`, `title` and `config`. Server-owned review, quota, pool, payout, status and audit fields remain in the response rather than the edit body.

Call `task_market_task_update_draft` with a stable idempotency key. On a concurrent-change conflict, read the current detail and reconcile the requested edit before submitting a new replacement. Re-read the saved Task after success; the same Account sees it on Web. On a timeout or unknown result, read that original Task before deciding whether to retry the identical request with its original key.

Drafts under Finch review are locked. A published, funded Task can be edited only before its existing start time, with a future replacement start before its deadline. Its chain, funded reward, reward slots, settlement mode and pool terms remain fixed; the funded `merchant_review_7d` end time is also fixed. Standard funded Tasks cannot be changed into Tasks requiring Finch publication review, and published Tasks already requiring that review remain locked. The server applies the same content and schedule rules as Web and returns the specific refusal when the requested change is outside them. To delete, call `task_market_task_delete_draft` only for the explicitly selected draft with its own idempotency key; pending-review or published Tasks cannot be deleted.

1. Collect the title, instructions, collaboration and settlement modes, verification requirements, reward asset and amounts, submission limits, deadline, and participant constraints. Do not invent review policy or funding.
2. Create the draft and check its publication-review state before preparing publication through MCP. The four new Finch-reviewed Custom Task presets use `publication_custom`: website registration, product onboarding, product/feature trial, and form completion. They require Finch approval of the current revision before funding; standard goals and the legacy advanced `custom` goal retain their own rules. For publication review, use the mounted `task_market_task_submit_publication_review` and the workflow below. If the environment has not exposed it yet, use the same Account's supported Browser review flow and wait for approval. Do not invent an MCP tool or fund an unapproved revision. After approval, call `identity_actor_get`, compare it with `finch status`, and hard stop if Account, wallet, or environment differs. Inspect the frozen pool preparation, show the exact transaction summary for approval, then run the returned `finch task publish-submit <TASK_ID> --intent <INTENT_ID>` action. It validates authority, broadcasts once, checkpoints the hash, and confirms atomically. Re-read approval after content changes; recover an existing funding operation through its returned recovery action instead of creating a second pool.
3. Re-read the Task and require the expected open and funded state.
4. Read the review board. For each user-authorized decision, prepare review through MCP, repeat the MCP/CLI identity comparison, show the award summary, and run the returned `finch task award-sign <TASK_ID> --intent <INTENT_ID>` action. The command records one EIP-712 signature batch and confirms review atomically; the runtime broadcasts the award. Do not create another signature batch after an unknown response. Verify approved submission, participation, award operation, fee, and remaining pool.
5. Reclaim only when the user explicitly requests it and the Task is eligible: prepare through MCP, repeat the identity comparison, show the transaction summary, and run the returned `finch task reclaim-submit <TASK_ID> --intent <INTENT_ID>` action. It broadcasts once, checkpoints the hash, and confirms atomically. Do not close or reclaim a Task merely to clean up a run.

Re-read the Task after the CLI confirms; the review receipt alone never proves funding or publication. Standard Tasks and legacy advanced `custom` Goals keep their existing publication rules.

### Original funding and reclaim recovery (CLI 0.5.6+)

Local `finch task recover` resumes a saved recovery record; CLI 0.5.7 adds explicit guidance when no local record exists. Successful confirmation clears that record; after a successful publish, award or reclaim, read the original operation and Task through MCP rather than running recovery. If the CLI reports no local recovery record while the original outcome is uncertain, use the original wallet/profile and the same Account to inspect `task_market_task_operations` before retrying. The absence of a local record alone does not prove completion or failure.

After a timeout or restart, call `task_market_task_operations` with the original `taskId` and optional `kind` (`publish`, `award`, `reclaim`). It requires requester read authority and returns only this Account's stored operations, in bounded pages. `prepared` means inspect the protected original CLI record; the server has not established whether the wallet signed or broadcast. `submitted` means confirm the original transaction or signature batch. `confirmed` records pool creation, actual award payment, or a sweep back to publisher Vault credit according to `kind`. A failed record requires reconciling that original operation. This read does not query the chain or execute anything.

Use an existing CLI journal's recovery command first when it contains signatures or a transaction. If `prepareRecovery` is present, reuse its exact tool, arguments and `idempotencyKey` with the original Account, wallet, environment and API origin and a currently authorized MCP grant. Publication and sweep preparation can return the original wallet intent. A submitted award instead returns its original batch with `requiresPublisherSignature:false`; confirm those same award IDs through MCP without signing again. Prepared awards intentionally have no automatic recovery reference: with no local journal after preparation response loss, reuse the saved original request parameters/key only under the existing preparation rules. An expired unsigned preparation may refresh its authorization and return a different immutable intent; that is not recovery of an earlier signed authorization. Preserve earlier journals and reconcile them first.

If a reference is absent or authority checks refuse it, retain the original journal and request parameters for reconciliation. A missing hash or preparation reference never authorizes a new pool, signature batch or payment. Successful same-key confirmations restore their original receipt; read the Task or review board separately for its latest state. This query and receipt repair require the matching service deployment and Skill distribution, with no additional CLI release beyond the existing original-transaction support below.

CLI 0.5.6 saves original signed bytes/hash/nonce before Task approval, pool funding, revocation and reclaim broadcast. A failed checkpoint save prevents sending. Use only the returned `finch task recover <TASK_ID> <publish|award|reclaim>` action under the original Account, wallet and environment. It preserves the frozen funding amount and original stage evidence, checks the original transaction and can replay only those same saved bytes when absent. A missing receipt is insufficient to rebuild or re-sign a payment. Old hash-only records retain their existing receipt/confirmation limits. Award recovery reuses its saved signatures; do not generate another batch.

A confirmed reverted receipt is a failed transaction with the original hash and any allowance-cleanup status retained. Follow the exact returned guidance for saved cleanup or unsent cleanup; successful cleanup ends recovery. Keep journals and reconcile the existing operation before preparing a separate new business action.

### Merchant review, settlement and regional admission

For `merchant_manual` and legacy `delayed_auto_7d` Tasks, merchants may review and select winners from the Task start time until seven days after the Task deadline, followed by two days of settlement grace. Neither mode automatically selects or awards remaining participants. Remaining funds become eligible for return to the merchant Vault at day nine, subject to the funded pool's immutable on-chain deadline and any dispute freeze. Report a return only after confirmed settlement evidence; elapsed time alone is not a receipt. Standard FCFS and weighted-lottery Tasks retain their respective automatic policies.

New collaborative Custom/Register Tasks using the seven-day review option use `merchant_review_7d`; an explicitly selected deadline lottery keeps its lottery policy. The merchant may review and select winners from the Task start time until seven days after the Task deadline. A rejected participant may contest through Get Help until day eight, and Ops decides between days seven and nine. On day nine the platform pays each participant's latest review-admitted, pending submission, including Review Later and upheld contests, in submission order until reward slots run out. An unresolved contest does not freeze settlement. The new pool expires six hours after day nine; remaining funds can be returned to the merchant Vault only after pool expiry and confirmed settlement evidence. Do not promise a reward to every participant, and do not try to approve or reject after day seven. Already-funded pools keep their original mode and chain terms; a funded merchant_review_7d Task's end time is locked.

`review_later` marks an unfinished decision; untouched entries also remain unfinished. Exhausting awards or returning funds does not approve or reject these entries. Use the returned review window and remaining capacity when preparing an explicit award. Browser Excel import previews selected wallets and revalidates evidence; it is not approval or payment, and still requires the existing explicit confirmation and signing flow.

Task creation restrictions and final-submission restrictions are independent region policies. In a restricted submission region, the Account limit is two final submissions across Tasks, not a daily allowance. Respect the server response; do not switch Accounts, clients, or network origin to bypass admission.

### Expired requester award reservations

For an explicit requester cancellation, use the mounted `task_market_task_prepare_review` with `action: "cancel_award"` and the exact submission IDs (at most 100 per headless request). Only expired, unused, unsigned and unrelayed merchant-controlled preparations can be released. The server verifies chain usage and expiry; the last valid on-chain second is still valid. A successful cancellation releases the reservation and returns the submission to pending without a new wallet signature. Reassign only if the Task award window remains open. This does not revoke an already paid reward.

For persisted or externally paid awards, recover the existing receipt instead of generating a second signature/payment. Separately paid or partially paid batches may require restoring each submission separately; obey the returned recovery error. Re-read the review board after cancellation or recovery before preparing new awards.

For the Web-compatible image-bearing Excel workflow:

1. Request `task_market_task_workbook_export` with Task ID, `locale:en|zh|zh-TW` and `selection:true` when marking merchant-selected winners. Run its `finch task workbook-export TASK_ID --out-file PATH [--locale LOCALE] [--selection]` using the same Account/environment CLI Session. Choose a new protected output filename; existing files are not overwritten. This needs CLI 0.5.7 or newer, whose help exposes `task workbook-export` and `task workbook-parse`. This Skill/service update does not install that executable.
2. Open and review the actual selection-template `.xlsx`, preserve the Finch template/identifiers, and mark intended winners. A plain report is not a selection template; a template with no marked winners returns `empty`. CSV is not accepted. Run `finch task workbook-parse --path FILE` locally. Its `selection` is an untrusted checked-row manifest, not an approval or payment. File limit is 32 MiB, at most 5,000 participant rows and 100 selected winners. Existing ZIP/XML, formula, macro and external-content protections apply. No workbook bytes or images are uploaded.
3. Pass the complete returned `selection` into `task_market_task_workbook_preview` with Task ID. Inspect every selected wallet and row issue. Stale proof, foreign/missing submissions, wallet changes, duplicates, ineligible entries, expired review or insufficient remaining slots must be corrected before continuing. A successful preview changes no winners.
4. Only after the merchant explicitly confirms the displayed list, call `task_market_task_workbook_prepare` with the same complete `selection`, `confirmed:true` and a stable idempotency key. First preparation rechecks current evidence under the shared transaction. Preserve the original key and identical manifest if the response is lost: this restores the original preparation/paid recovery even when the old Excel is now ineligible. A deliberately changed list needs a fresh preview, confirmation and key. Execute the existing returned publisher signing/confirmation flow and then query actual payout facts.

`task_market_task_close` ends owned open or not-started work early only after explicit merchant confirmation. It moves work to judging and leaves the original review deadline and TaskVault funds unchanged. It neither pays winners nor reclaims money. Retain its key after uncertain outcomes and read current Task state before any new action.
